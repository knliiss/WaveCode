# WaveCode V2 — single canonical experimental specification

**Status:** experimental in `experiment/v2`, not merged to `main`. Released V1 optical marks, APIs, and readers remain unchanged. This is the ONLY V2 specification file. Older experimental microhole/dotted W marks are intentionally not compatible with this new optical reader.

## Invariants and goals

- The original WaveCode W is the optical finder at the logical left, used to determine position, direction, scale and mild perspective.
- The W transmits **only the explicit 12-bit optical version**. There is NO platform routing profile, time information, track ID, checksum of identity or style information in the logo.
- The W has **22 solid rounded capsules and zero microholes**, allowing physical 3D-printing experiments without tiny perforations.
- The **source routing profile is moved to the FIRST ordinary dual-rail payload column**; all identity and moment bits remain behind it. The profile is not inferred from the W.
- `Classic` and `Compact` are only visual presets; they never alter `Frame.metadata`, `Frame.symbols`, identity or moment. The image scanner does not require knowing the preset.
- CRC-16/CCITT-FALSE covers the routing profile and identity payload, with four Reed–Solomon parity bytes protecting the identity payload and CRC.

## Geometry and exact 12-bit version in the W

The exact original brand geometry lives in `assets/brand/wavecode-mark.svg`. In the original 512×512 SVG coordinate system, eleven upper and eleven lower capsules have 20-unit width and a 34-unit horizontal step; centers are `x=86+34*i` for `i=0..10`. Upper ends face the fixed middle boundary `y=242`; lower starts face `y=274`. The **32-unit empty central channel and horizontal centers never vary**, and there are never small internal holes. Original upper heights are `[96,77,48,37,70,113,70,34,53,76,98]`, and lower heights `[30,50,70,87,59,31,56,85,66,47,29]`.

Each of the 22 capsules carries ONE protected version bit using a very small outward extension of its original length:

- Upper capsule bit `0` = original length; bit `1` = 5 original SVG units longer **toward its outer top** (upper edge moves up, central edge stays unchanged).
- Lower capsule bit `0` = original length; bit `1` = 5 original SVG units longer **toward its outer bottom** (lower edge moves down, central edge stays unchanged).
- Bit positions `0..10` are the upper capsules from left to right, positions `11..21` the lower capsules from left to right.
- The rendering canvas includes 5-unit extra vertical room on both sides (scaled); the 32-unit central gap is preserved.
- Five SVG units are about 0.42 mm at a printed W width of 30 mm. This is a geometric difference, **not a guarantee** that a particular printer or camera resolves it.

### Version BCH(22,12,d≥5)

Take binary primitive narrow-sense BCH(31,21,d≥5) with GF(32) polynomial `x^5+x^2+1`; the binary generator is `0x769` (degree 10). Shorten nine leading information coordinates to derive **BCH(22,12,d≥5)**. For `version ∈ [0,4095]`:

```text
m = version
word22 = (m << 10) OR remainder_GF2((m << 10), generator=0x769)
```

Place the 22 bits **most-significant first** into the upper then lower capsules. No routing profile or aesthetic selector enters this operation.

The code is linear. Exhaustive enumeration of all 4095 nonzero version codewords finds minimum Hamming weight **5**; therefore minimum distance is 5. Any one or two incorrectly classified capsule-length bits can be corrected uniquely; three or more are NOT guaranteed correctable or even detectable. The camera must still identify the actual 22 bars before this algebraic guarantee applies.

The reader first recognizes the characteristic W spacing, pairs capsule components, resolves camera roll, and estimates each capsule's **local scale from neighboring column centers**. It measures relative lengths, BCH-decodes the 12-bit version, requires exact `version=2`, and only then reads payload columns. W orientation tells the scanner the positive logical direction toward data. This method is significantly less demanding to manufacture than 60 tiny negative-space holes, but requires physical testing for length classification and severe perspective.

## Payload profile, byte mapping and styles

The `Frame` type retains `metadata: u8` and `symbols: Vec<u8>` so applications can use exactly the same lossless content codec. Its `metadata` is encoded optically as **one additional leading 8-bit payload symbol** (profile 0..15 currently used; 16..63 reserved). Following that column are the normal CRC-16 / four-byte Reed–Solomon protected `symbols`. The existing CRC calculation includes the profile byte and therefore rejects a mismatched or misread header, but **the first profile column is not itself covered by the existing RS parity**. Before release, decide whether header error correction should be strengthened. Never claim RS can repair this independent prefix under the present implementation.

### Independent 256-symbol optical alphabet and freely chosen gaps

Each byte appears as two opposed capsules of **constant width** and 16 height levels: `upper = byte >> 4`, `lower = byte & 15`. Physical rail height is `H × (0.085 + 0.022 × level)`, width is `0.75 × pitch`. No information is encoded in width, central gap or W-to-payload gap. `Classic` has `pitch=18, H=210, quiet=18`; `Compact` has `pitch=16, H=210, quiet=16`.

**Both whitespace distances are visual-only and independent.** `VisualSpacing` accepts:
- `payload_center_gap` — actual white distance between payload's upper and lower capsule boundaries, in output pixels;
- `logo_payload_gap` — actual white distance from the rightmost edge of W to the first payload capsule, in output pixels.

Both default to values chosen for V2 aesthetics: `payload_center_gap = 16 × H/232` (about **14.48 px** at H=210, half the W's 29 px white channel), and `logo_payload_gap = 1.4 × pitch` (**25.2 px Classic**, **22.4 px Compact**), larger than the preceding version. The original W has **its own unchanged 32-unit SVG central slit**.

Renderer interfaces: `RenderProfile::metrics_with_spacing`, `render_svg_with_spacing`, `render_png_with_spacing` in Rust; `v2_render_svg_with_spacing` / `v2_render_png_with_spacing` in WASM. Existing style/default renderers use `VisualSpacing::for_profile`, so existing calls remain valid.

### Canonical center, independent white slits

**The vertical reference is the midpoint of the W's slit, never the midpoint of its black silhouette.** In the original SVG the upper slit border is `y=242`, lower is `y=274`, so the center is `C_svg=258`. In the W-local coordinate system, with `s=H/232` and `y=129` as origin:

```text
C_local = (258-129)*s = 129*s
W upper inner baseline = (242-129)*s = 113*s
W lower inner baseline = (274-129)*s = 145*s
W slit size = 32*s [unchanged]

P = VisualSpacing.payload_center_gap [visual-only]
G = VisualSpacing.logo_payload_gap [visual-only]
payload upper inner baseline = C_local - P/2
payload lower inner baseline = C_local + P/2
payload max rail height = 0.415*H
payload first capsule left edge = quiet + 360*s + G
payload_x (first column cell) = quiet + 360*s + G - (1-0.75)*pitch/2

W upper outer bound = -5*s
W lower outer bound = (232+5)*s
full top bound = min(-5*s, payload_upper_baseline-0.415*H)
full bottom bound = max(237*s, payload_lower_baseline+0.415*H)
margin = max(8px,0.038*H)
canvas height = full_bottom-full_top+2*margin
Y offset = margin-full_top
```

Apply the same Y offset to W and payload; the payload's two allowed extrema remain mirror-symmetric around the **W slit center**, although their empty central gaps are not required to match. No bar is clipped when P changes: the canvas grows with the bounds. A screenshot, print or scanner receives *only the visible marks*: neither P nor G is written into `Content`, `Frame`, metadata, or the W version.

### Scanner must not assume either gap

The reader locates the 22 solid W capsules using their characteristic shape, spacing and version-length code. It **excludes those specific identified W components** and then locates the separate payload components to their logical right, without checking an expected W-to-payload distance. Upper and lower payload rails are paired by their observed horizontal positions; their individual heights recover the 16-level symbols. The reader does **not** compare the observed central payload gap to the W gap or to a constant. Neither a preset name nor a gap measurement is an input to the decoder.

The synthetic optical test suite varies both gaps independently across several values, including tight but separated and very spacious layouts, and checks the unchanged decoded URL under rotations and inverted contrast. This is a guarantee about the **format's independence from decorative distances**, not a claim that every imaginable physical mark remains readable: zero or blurred-out whitespace merges connected bars, very large bitmaps hit image-size resource limits, and strong blur, reflections, foreshortening or print defects can make components indistinguishable. The renderer requires both gaps to be finite and at least 2 px on its output scale.

The complete optical column budget for `B` encoded identity+moment bits is:

```text
N_optical_columns = 1_profile + ceil((B + 16_CRC) / 8) + 4_RS
```

The existing `Frame.symbols.len()` counts the **protected data columns only**; it does not include the separate optical profile prefix. Example: canonical 64-bit YouTube Music ID uses 14 RS-bearing source columns plus 1 profile column = **15 visible payload columns**. This changes only experimental V2 marks, not V1.

The W has exactly the same version geometry in `Classic` and `Compact`; no payload spacing value is encoded or implied by the optical version. Styled bytes remain unchanged. Sixteen height levels require good resolution; aesthetic preference alone is not proof of camera reliability.

## Implemented source profiles and losslessness

All source profile IDs remain unmodified, and identities are never approximated or truncated. The profile header is now physically in the payload, NOT inside the W.

Older *source layout* modes `0,2,4,6,8,10` remain available under the new V2 optical finder. Their former pre-release **optical marks** are NOT compatible.

For numeric tag families: `0=Deezer,1=Tidal,2=Qobuz,3=TikTok`, with no TikTok moment in profile 7. 32-bit numeric IDs, 128-bit Spotify rank, canonical 64-bit YouTube video rank, and seconds 0..255 are **conditional** short modes. Every supported input outside such a mode uses the lossless full-width fallback. `v2::encode_adaptive` selects the shortest valid source profile; `v2::encode` retains the previous source selection but uses the same new W and optical payload. A 16-bit CRC detects reinterpretation under the wrong profile, subject to normal CRC collision probability.

## Source-ranking research (historical, not the current optical format)

**Historical assumptions** below predate version-only W. Every source-only column count in this section excludes the additional physical routing-profile column. Any claim that a profile is **stored in W** is obsolete; the profile is optically in payload. This section concerns theoretical source-rank bounds, NOT a current W codebook.

The following results are mathematics or potential future optimizations. They do **not** authorize changing the current source format or reinterpreting metadata IDs without a tested migration.

#### Theorem 1: what cannot be compressed

For a domain `S` containing `N` different admissible identifiers, a
losslessly reversible fixed-width encoder is an injection `E:S->[0,2^b)`.
Therefore `N<=2^b`, so the tight lower bound is

`b_min = ceil(log2(N))`.

For arbitrary 22-character Spotify Base62 strings,
`N_S=62^22`, `log2(N_S)=130.9923188285...`, hence **131 bits**.
The Spotify developer documentation describes Base62 IDs but does **not**
promise that every valid ID is 128-bit. Indeed, a documented popular Spotify track ID
`7qiZfU4dY1lWllzX7mPBI3`, interpreted with the repository's Base62
alphabet, has numeric bit length **129**. Never unconditionally assume 128 bits,
UUIDv4 structure, or six fixed UUID bits.

For a canonical YouTube 11-character Base64URL video ID, the final Base64
digit must be divisible by 4: the last **two bits are zero**, so its cardinality
is `2^64` and its exact reversible rank needs **64 bits** (not 66).
This is a documented property of the canonical 64-bit ID format; do not apply
it silently to arbitrary 11-character strings.

For an *independent* Spotify + canonical YouTube Music pair, the domain is a
Cartesian product and needs

`ceil(log2(62^22 * 2^64)) = ceil(194.9923188285...) = 195 bits`.

An optimal rank is `R = spotify_base62_rank * 2^64 + youtube_u64`.
Decode with `spotify_rank = R >> 64` and `youtube_u64 = R mod 2^64`.
This is collision-free. No offline algorithm can represent **all** such
independent pairs in 194 fixed bits, even if the algorithms are new or complex.

An entropy coder (arithmetic, ANS, Golomb, etc.) cannot defeat this
worst-case bound. If real IDs are statistically nonuniform, a self-contained
fixed source model may improve **expected** length; it must have a reversible
escape route, be reproducible by the decoder, and be evaluated on representative
held-out IDs. Do not claim such a distribution or savings without evidence.

#### Theorem 2: adaptive disjoint-domain rank (WaveCode ADR)

Instead of concatenating `platform_tag | storefront | ID`, partition the
accepted input set into known, disjoint finite domains `S_0..S_m`. Each has
a reversible rank `r_i(x)` in `[0, N_i)` and an agreed order. Define:

`offset_i = sum_{j<i} N_j`
`E(i,x) = offset_i + r_i(x)`.

The decoder finds the unique interval `[offset_i, offset_i+N_i)`, subtracts
`offset_i`, and calls the inverse `r_i^-1`. Disjoint intervals prove
**injectivity**, and every integer in `[0,sum N_i)` has an inverse.
Thus the method reaches the optimal width for the whole profile:

`b = ceil(log2(sum_i N_i))`.

This is a custom *engineering composition* of known enumerative/mixed-radix
coding principles, **not** a claim to have invented a new mathematical theorem.

#### Surprising case: reuse impossible Apple storefront values

The current 2-letter lower-case Apple storefront grammar has exactly
`26*26=676` possible tags, while its 10-bit field has `1024` values.
Therefore **348 namespace slots are unused**. If a payload profile says
"Apple-or-numeric family", reserve tag `0..675` for Apple storefronts, and
`676..679` for four numeric-ID platforms (TikTok, Deezer, Tidal, Qobuz).

Let `T` be that 10-bit group and `x` the entire 64-bit ID:

`R = (T << 64) | x`, `0<=T<680`, `0<=x<2^64`.

Decoding is exact: `T = R >> 64`, `x = R mod 2^64`; for Apple,
`country[0]=floor(T/26)`, `country[1]=T mod 26`.
All **680** groups still fit **74 bits**, exactly the same width as an
Apple storefront plus ID alone: `ceil(log2(680*2^64))=74`.
This folds four whole platform namespaces into unused valid field states
**without adding a bit**. It does not, by itself, shorten Apple's existing
74-bit contents, and specialized short-ID profiles remain better for small
numeric identifiers. Tags must be stable and versioned.

The general optimization for `m` subordinate namespaces is: pack all
admissible variants inside the unused states of an existing bounded field
before allocating new tag bits.

#### Theorem 3: range-tier modes with explicit fallback

For each admissible interval `[a_i,b_i)` of integer IDs, W metadata may
select the **range class** (not any identity bit), while payload stores
`x-a_i` in `ceil(log2(b_i-a_i))` bits. The decoder computes `x=a_i+r`;
it checks `r<b_i-a_i`. This is reversible and optimal *within the class*.

Example: a platform's 64-bit numeric ID uses **32 bits** when `x<2^32`
and **64 bits otherwise**. The latter route is mandatory; this is not
universal 32-bit compression. The two-bit 4-service tag can be added inside
the payload if the W profile identifies a numeric-family layout.

More sophisticated schemes can use intervals based on an analytically
specified model (not a lookup table of songs). A mode selector can choose
the shortest admissible representation **after accounting for all headers,
CRC, RS, column rounding and W overhead**.

#### Theorem 3a: harvest byte-alignment slack for **free moments**

A byte-aligned Reed-Solomon block wastes some of its final data byte.
For `b` source bits, fixed CRC-16 and four parity bytes, the number of
unused pre-RS bits is exactly:

`slack(b) = 8*ceil((b+16)/8) - (b+16)`, in `[0,7]`.

A separately designated W time-width profile may put a `t`-bit moment
inside these unused positions with **zero change in payload column count**
whenever `t<=slack(b)`. The moment is still part of the CRC-covered source
message. The decoder learns its exact width from mode metadata; values
outside the window use a longer fallback.

Examples under the research profiles:
- Full 131-bit Spotify rank: `slack(131)=5`, so times 0..31 seconds
  can be represented **inside the same 23 payload columns** as no moment.
- Canonical independent Spotify+YouTube pair: `slack(195)=5`, giving
  an exact 0..31-second moment **inside the same 31 columns**.
- Four-service 32-bit numeric mode: `b=2+32=34`, `slack(34)=6`,
  so up to 63 seconds can be represented in the same **11 columns**.
- Canonical YouTube Music, `b=64`, `slack(64)=0`: there is no
  extra room without an additional column.

This is a measurable **bit-allocation optimization**, not a compression of
uniformly random data. A W mode explicitly marking tiny time is necessary:
without it, a decoder would mistake those bits for zero padding.
W continues to hold *only* routing metadata.

#### A practical impossibility bound: 13-column universal YouTube

Suppose a **single** W layout must encode any of the `2^64` canonical
YouTube identities in 13 byte-carrying payload columns, without weakening
CRC-16 or four RS parity bytes. Only `13-4-2=7` data bytes remain: at most
`2^56` distinct IDs fit, which is just **1/256** of the required domain.
Therefore **13 payload columns cannot cover all 64-bit YouTube IDs** with
the same protection and the current eight-bit optical alphabet.

Even generously allocating **all 16** distinguishable W metawords to
different 13-column routing classes yields at most
`16 * 2^56 = 2^60 < 2^64` identities, and that would leave no metadata
states for any other layout or timestamp. With no ID data permitted in W,
a 14-column specialized canonical-YouTube frame is the firm lower bound
**within the present CRC+RS byte-frame construction**. This is not a claim
that every conceivable nonlinear channel code needs 14 symbols: the
claim expressly assumes unchanged CRC-16 and four systematic RS bytes.

#### Another bound: variable optical length is not free storage

If a decoder reliably distinguishes length classes `b_1,..,b_k` and their
routing modes, their *combined* capacity is at most
`sum_i 2^(b_i)`. Length is useful **side information**, but it cannot
magically carry dozens of bits in a code with only a few detectable lengths.
In particular, shorter variants cannot represent all inputs from a uniform
large space; there must always be fallback. Nor can the W's sixteen
metawords provide an extra eight payload bits: the absolute maximum is
four bits **before** subtracting the mandatory layout metadata.

**Profile count update:** the original adaptive-research analysis assumed a four-bit routing header with only 16 possible values. The current W transmits a **six-bit profile** with 64 values, of which 16 currently have codec implementations. Old scarce-header allocation arguments must use this updated capacity; packing identities into W is still forbidden.

## WASM, CLI and verification

WASM entry points remain opt-in: `v2_encode_url`, `v2_encode_dual`, `v2_render_svg`, `v2_render_png`, `v2_render_svg_style`, `v2_render_png_style`, `v2_decode_frame`, `v2_scan_image`. JSON frames retain `metadata` for application interoperability; it is encoded **as the first payload column** and does NOT modify W. The scanner returns exact version, decoded payload profile, BCH correction count and W pose.

For Windows PowerShell (commands on ONE line, or use the PowerShell backtick to continue):

```powershell
git fetch origin
git switch experiment/v2
git pull
cargo test --workspace
cargo run -p wavecode --example v2_experiment -- encode-adaptive "https://music.youtube.com/watch?v=JGwWNGJdvx8&t=59" classic.png classic
cargo run -p wavecode --example v2_experiment -- encode-adaptive "https://music.youtube.com/watch?v=JGwWNGJdvx8&t=59" compact.png compact
cargo run -p wavecode --example v2_experiment -- scan classic.png
cargo run -p wavecode --example v2_experiment -- scan compact.png
```

Each output is a real PNG plus SVG. The W is represented as **22 solid capsule rectangles and zero microholes**. The V2 preview GitHub Actions workflow verifies both render styles by scanning generated images before exporting artifacts.
