# WaveCode V2 — optical format, source profiles and implementation status

**Canonical V2 specification.** This is the **only V2 document** in `spec/`. It defines the current experimental code in `crates/wavecode/src/v2/`, its mathematical limits and the release gates. **V2 is not yet released or merged to main**. The production V1 encoder, decoder, scanner, API, and printed marks remain unchanged.

## Scope and invariants

- Every V2 mark begins with a W-shaped **round-dot locator** to the logical left of the data. The discontinued experimental 11-pair capsule-W locator is **not** emitted or accepted by the current V2 optical scanner. Do not use older commits as a specification for newly printed V2 marks.
- The W holds **only routing metadata**: version, source profile and aesthetic selector. No music identity bits, shortened ID hashes, URL fragments, or track lookup database are permitted in the W.
- All identifiers and moments remain lossless and self-contained. Encode/decode is deterministic and offline, with full-range fallbacks. No platform network requests are necessary to read a mark.
- Preserve CRC-16/CCITT-FALSE and four GF(256) Reed–Solomon parity **bytes** for the payload. A four-byte parity budget corrects at most two unknown damaged payload columns, or up to four located erasures.
- All code changes and experiments belong to `experiment/v2`; never create a new branch per subfeature. Any V2 format change that invalidates already printed experimental marks needs an explicit compatibility decision before release.

## W geometry, exact version and six-bit-error correction

### Geometric blueprint

All coordinates are normalized and deterministic. The W spine is the polyline:

```text
(0,0) → (4,10) → (8,1.6) → (12,10) → (16,0)
```

Each of the four segments has a unit normal N. The immovable contour comprises candidate sites sampled 17 times per segment on the two offset rails **P(s) ± 1.55 N**. Keep sites more than 0.62 units from *every* segment of the spine and at least 0.84 units from other contour sites. Its fixed circular radius is **0.32** normalized units. This forms the permanent outside and inside stroke boundaries, including the upper and lower extrema.

Generate internal candidates between the boundaries on the offset rails **P(s) ± 0.78 N**, with respectively 11, 10, 10, 11 candidate sites per segment per side. Keep only centers more than 0.57 units from the complete spine, more than 0.72 units from contour centers, and more than 0.62 units from earlier interior centers. Select **60** evenly distributed sites across the entire W, not just the first arms. Only those inner circles change radius: **0.165 for 0** and **0.235 for 1**. Their centers never move.

Shift the normalized sites by (2.0,1.2) into a **20.0 × 12.5** bounding coordinate frame. The image scale is **height × 0.055** pixels per normalized unit. The payload begins to the right of the W's reserved width, with a quiet gap. This geometry is shared by the SVG/PNG writers and the scanner.

The forbidden white channel is the constant tube around the complete W spine. The measured geometric clearance from the spine to every circle edge is **at least 0.30 normalized units** for fixed contour circles and **at least 0.35** for inner variable circles. Thus the center-line negative space is independent of all metadata. Variable radii cannot modify the outside silhouette because all variable centers lie strictly inward from the fixed-boundary centers with clearance. The central upper crest, both lower valleys, and their adjacent negative spaces are fixed features. The current deterministic grid resolves to **57 fixed contour circles plus 60 variable inner circles**, 117 in the W overall.

### Encoded bits

| Property | Bits | Range |
| --- | ---: | --- |
| Exact optical format version | 12 | 0..4095; V2 emits 2 |
| Payload decoding profile | 6 | 0..63 |
| Deterministic visual selector | 6 | 0..63 |
| Frozen BCH subcode bits | 3 | always 0 |
| BCH check bits | 33 | not user data |
| **Total circular information sites** | **60** | one bit per dot |

The visual selector allows **64 distinct BCH-valid patterns for each (version,profile)**, all of which recover identical routing metadata. The encoder chooses the minimum deterministic cost by balancing the fraction of larger inner marks across the four W arms and discouraging neighboring marks with equal sizes.

### Mathematical derivation

Take the primitive narrow-sense binary BCH code of length 63 over GF(64), primitive field polynomial `x^6+x+1`, with roots alpha^1 through alpha^12. Its six binary cyclotomic cosets have sizes **6,6,6,6,3,6**. Thus its generator has degree 33, dimension **63−33=30**, and BCH lower bound **d ≥ 13**.

Its generator polynomial is

```text
g(x) = 0x37cd0eb67
     = m1(x) * m3(x) * m5(x) * m7(x) * m9(x) * m11(x)
```

where the minimal factors in bit-packed form are `0x43, 0x57, 0x67, 0x49, 0x0d, 0x6d`.

Shorten three leading message coordinates, obtaining the **(60,27,d≥13)** code. Freeze another three of its message coordinates to zero, obtaining a **(60,24,d≥13) subcode**. This differs from the incorrect assertion that BCH(63,27,d≥13) itself was the original primitive BCH code.

Let `M=(version<<12)|(profile<<6)|shape`, with 24 bits. The 60-bit codeword is

```text
X = M << 36
W = X XOR rem_g(X)
```

The middle three message positions immediately above the 33 parity bits are fixed zeros. All 60 bits are placed MSB first in the deterministic spatial permutation `site_bit = (17*site_index) mod 60`. Since gcd(17,60)=1, every code bit has exactly one dot.

Since `d ≥ 13`, every error vector of Hamming weight **at most six** has a unique decode. The prototype uses a meet-in-the-middle syndrome lookup: enumerate all **36,051** patterns of weight at most 3; for a received syndrome S, find two patterns with `S1 XOR S2 = S` whose combined weight is at most 6. Check the corrected polynomial remainder and the three frozen zeros. The minimum-distance proof guarantees that at most one corrected word lies within radius six.

This guarantee is **only for incorrect dot bits after geometric matching**, not for arbitrary missing circles, blobs, occlusion or an incorrectly localized W. Payload checksums (CRC16+four RS symbols) remain separate.

### Scanner contract

1. Locate the round-dot W from connected components and fit the static contour geometry.
2. Match the canonical dot sites to observed circle centers; allow a bounded number of unmatched low-resolution inner circles.
3. Normalize dot areas against the fixed-radius contour; decide the 60 bit values.
4. BCH-decode and explicitly reject optical versions other than 2.
5. Read the dual-rail payload to the right of the W and decode its profile, CRC16 and RS parity.

The scanner supports 90° rotations and experimental moderate roll/keystone test cases, but actual phones and printed miniatures require field validation.

## Source payload and byte-column format

The optical payload follows the W and consists of two capped rails per byte: upper height 3 bits, lower height 3 bits, upper width 1 bit and lower width 1 bit. A source bitstream is zero-padded to whole bytes, its one-byte profile header and payload are protected by CRC-16/CCITT-FALSE, and four RS parity bytes are appended. Every final GF(256) byte occupies **one** pair of bars. For `B` source bits, `columns(B)=ceil((B+16)/8)+4` (the W, gap and quiet zones cost extra physical width).

The payload metadata (profile) is now a 6-bit field inside the **60-dot BCH W**. The current source decoder uses header values 0..15; 16..63 are reserved for future payload profiles. Its existing accepted source layouts are retained; expanding the W from four to six profile bits does **not** mean all 64 profiles are implemented.

### API selection

- `v2::encode(&Content)`: previous nonadaptive source layouts, but **rendered with the current 60-dot W**; not a legacy rectangular optical format.
- `v2::encode_adaptive(&Content)`: evaluates reversible candidate source layouts and chooses the shortest payload in byte-columns; ties keep the existing layout. V2 WASM `v2_encode_url` and `v2_encode_dual` call this adaptive encoder.
- `v2::decode(&Frame)`: validates the selected profile, CRC and RS-protected source block.
- `v2::visual::render_svg/render_png` and `v2::raster::scan_png_or_jpeg`: write/read the current W+payload. Optical scanning returns the exact version/profile and the count of repaired BCH metadata bits.

### Implemented adaptive source profiles

### Exact new metadata assignments and bit ordering

All integers are written most significant bit first. Logical data bits
are zero-padded to whole bytes. CRC-16/CCITT-FALSE is computed over one
metadata byte followed by the padded message bytes. The 16-bit CRC is
appended in big-endian order, then four Reed-Solomon GF(256) parity bytes
are appended. Each resulting byte occupies one optical payload column.

| Meta | Data bits (before CRC) | Data bits | Columns |
| --- | --- | ---: | ---: |
| 1 | canonical YouTube Music rank (64) | 64 | 14 |
| 3 | YouTube Music (64) + seconds (8) | 72 | 15 |
| 5 | numeric-service tag (2) + ID (32) | 34 | 11 |
| 7 | numeric-service tag (2) + ID (32) + seconds (8) | 42 | 12 |
| 9 | Spotify Base62 rank (128) | 128 | 22 |
| 11 | Spotify rank (131) + seconds (8) | 139 | 24 |
| 12 | Spotify rank (128) + seconds (8) | 136 | 23 |
| 13 | Spotify rank (131) + canonical YouTube rank (64) + seconds (8) | 203 | 32 |
| 14 | Spotify rank (128) + canonical YouTube rank (64) | 192 | 30 |
| 15 | Spotify rank (128) + canonical YouTube rank (64) + seconds (8) | 200 | 31 |

Headers `0, 2, 4, 6, 8, 10` preserve their historical V2 layouts.
No old accepted header is reinterpreted.

For numeric-service tags, the profile uses:
`0=Deezer`, `1=Tidal`, `2=Qobuz`, `3=TikTok video`.
Profile 7 rejects tag 3, since a TikTok moment is not supported in the
current domain model. Every service has a 64-bit fallback through
historical V2. This 32-bit fast path represents **only** IDs in
`[0,2^32)` and includes the exact upper boundary value `2^32-1`.

The Spotify Base62 rank uses the unchanged 22-character alphabet:
`0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz`.
The 128-bit modes apply **only** to ranks below `2^128` and have a
131-bit fallback for all other Base62 strings; no ID is truncated.

A YouTube Music ID is considered canonical for these new modes only if
its 11 Base64URL digits have two zero low-order bits. Its 66-bit
representation is divided by four to get a 64-bit rank. On decode,
multiply that 64-bit rank by four and restore exactly 11 Base64URL
digits. Noncanonical-but-supported 11-character IDs remain supported
by the historical 66-bit fallback, with their original digits intact.

Seconds up to 255 are represented **exactly** by 8 bits. Anything greater
uses the unchanged 16-bit fallback. An absent moment is distinct from a
zero-second moment through the explicit W header.

### Reversibility and protection

### Mathematical proof of reversibility

Each profile fixes all field widths and their order via its metadata
header. A width-\(b\) unsigned integer maps bijectively to its \(b\)-bit
binary representation. Spotify base62-to-integer conversion is bijective
within its accepted range; YouTube divides an integer divisible by four
by four, which is a bijection onto the canonical 64-bit space.
Concatenation of fixed-width fields is injective. The numeric platform
tag distinguishes the four disjoint namespaces.

The profile and mode are protected with the frame CRC; this prevents a
different valid metadata word from silently interpreting an existing
payload as another profile except with the standard CRC collision
possibility. This is **error detection**, not cryptographic
authentication.

Let \(k=\lceil(B+16)/8\rceil\) be the information-and-CRC bytes for
\(B\) source bits. Each frame carries exactly \(k+4\) payload columns;
four RS bytes can correct up to two incorrect byte symbols. The
invariant \(D(E(x))=x\) is verified for examples, boundaries, all ten
metadata modes and two deliberately corrupted columns.

The complete printable width also includes the W locator, gap and
quiet zones; saving one payload byte does not imply one millimeter of
minimum readable print width.

### Payload length examples and mathematical lower bounds

### Column budgets: same CRC-16 + 4 RS bytes

For `B` information bits, with the entire logical mode available via W:

`columns(B) = ceil((B+16)/8) + 4`.

Here `+16` is CRC, and `+4` is RS parity *bytes*. These are **payload**
columns; W, separation and optical quiet zones are additional.

| Case | Identity/time bits B | Payload columns | Conditions |
| --- | ---: | ---: | --- |
| Existing V2 YouTube Music no moment | 4+66=70 | 15 | 4-bit in-payload service tag |
| Specialized YouTube Music no moment | 64 | **14** | Canonical ID, service metadata in W |
| Specialized YouTube Music, t<=255 | 64+8=72 | **15** | Time-width metadata in W |
| Existing V2 Spotify no moment | 131 | 23 | Full fallback |
| Spotify ID with rank <2^128 | 128 | **22** | Range-class metadata in W |
| Spotify any rank, t<=255 | 131+8=139 | **24** | Full rank and short time |
| Spotify rank <2^128, t<=255 | 128+8=136 | **23** | Conditional fast path |
| Existing V2 Dual no moment | 131+66=197 | 31 | Arbitrary YouTube 11-char input |
| Canonical Dual no moment | 131+64=195 | 31 | 195-bit lower bound achieved |
| Canonical Dual, t<=255 | 131+64+8=203 | **32** | Compared to 33 today |
| Spotify rank <2^128 + canonical YouTube | 128+64=192 | **30** | Subset fast path |
| Spotify rank <2^128 + canonical YouTube, t<=255 | 128+64+8=200 | **31** | Compared to 33 today |
| Four-service numeric family, ID <2^32 | 2+32=34 | **11** | 2-bit platform tag, no moment |
| Apple + four numeric services, full ID | 74 | 16 | 680-group combined rank |

The 128-bit Spotify fast path can represent only a subset. If all `62^22`
Base62 strings were equally likely, that subset would have probability
`2^128 / 62^22 = 0.1256672976...`, i.e. about **12.57%**.
Actual Spotify IDs may have a different distribution; this is not a measured
success rate. No rule is allowed to *truncate* or silently wrap any rank.

If `T` is an arbitrary 16-bit timestamp, worst-case time takes 16 bits.
An explicit "short moment" profile can represent exactly 0..255 seconds in
8 bits, with a 16-bit fallback. Do not quantize or silently lose seconds.

## Further source-ranking research — **not necessarily implemented**

The following results are mathematics or potential future optimizations. They do **not** authorize changing the current source format or reinterpreting metadata IDs without a tested migration.

#### Theorem 1: what cannot be compressed

For a domain `S` containing `N` different admissible identifiers, a
losslessly reversible fixed-width encoder is an injection `E:S->[0,2^b)`.
Therefore `N<=2^b`, so the tight lower bound is

`b_min = ceil(log2(N))`.

For arbitrary 22-character Spotify Base62 strings,
`N_S=62^22`, `log2(N_S)=130.9923188285...`, hence **131 bits**.
The Spotify developer documentation describes Base62 IDs but does **not**
promise that every valid ID is 128-bit. Indeed, a documented popular Spotify track ID
`7qiZfU4dY1lWllzX7mPBI3`, interpreted with the repository's Base62
alphabet, has numeric bit length **129**. Never unconditionally assume 128 bits,
UUIDv4 structure, or six fixed UUID bits.

For a canonical YouTube 11-character Base64URL video ID, the final Base64
digit must be divisible by 4: the last **two bits are zero**, so its cardinality
is `2^64` and its exact reversible rank needs **64 bits** (not 66).
This is a documented property of the canonical 64-bit ID format; do not apply
it silently to arbitrary 11-character strings.

For an *independent* Spotify + canonical YouTube Music pair, the domain is a
Cartesian product and needs

`ceil(log2(62^22 * 2^64)) = ceil(194.9923188285...) = 195 bits`.

An optimal rank is `R = spotify_base62_rank * 2^64 + youtube_u64`.
Decode with `spotify_rank = R >> 64` and `youtube_u64 = R mod 2^64`.
This is collision-free. No offline algorithm can represent **all** such
independent pairs in 194 fixed bits, even if the algorithms are new or complex.

An entropy coder (arithmetic, ANS, Golomb, etc.) cannot defeat this
worst-case bound. If real IDs are statistically nonuniform, a self-contained
fixed source model may improve **expected** length; it must have a reversible
escape route, be reproducible by the decoder, and be evaluated on representative
held-out IDs. Do not claim such a distribution or savings without evidence.

#### Theorem 2: adaptive disjoint-domain rank (WaveCode ADR)

Instead of concatenating `platform_tag | storefront | ID`, partition the
accepted input set into known, disjoint finite domains `S_0..S_m`. Each has
a reversible rank `r_i(x)` in `[0, N_i)` and an agreed order. Define:

`offset_i = sum_{j<i} N_j`
`E(i,x) = offset_i + r_i(x)`.

The decoder finds the unique interval `[offset_i, offset_i+N_i)`, subtracts
`offset_i`, and calls the inverse `r_i^-1`. Disjoint intervals prove
**injectivity**, and every integer in `[0,sum N_i)` has an inverse.
Thus the method reaches the optimal width for the whole profile:

`b = ceil(log2(sum_i N_i))`.

This is a custom *engineering composition* of known enumerative/mixed-radix
coding principles, **not** a claim to have invented a new mathematical theorem.

#### Surprising case: reuse impossible Apple storefront values

The current 2-letter lower-case Apple storefront grammar has exactly
`26*26=676` possible tags, while its 10-bit field has `1024` values.
Therefore **348 namespace slots are unused**. If a W metadata profile says
"Apple-or-numeric family", reserve tag `0..675` for Apple storefronts, and
`676..679` for four numeric-ID platforms (TikTok, Deezer, Tidal, Qobuz).

Let `T` be that 10-bit group and `x` the entire 64-bit ID:

`R = (T << 64) | x`, `0<=T<680`, `0<=x<2^64`.

Decoding is exact: `T = R >> 64`, `x = R mod 2^64`; for Apple,
`country[0]=floor(T/26)`, `country[1]=T mod 26`.
All **680** groups still fit **74 bits**, exactly the same width as an
Apple storefront plus ID alone: `ceil(log2(680*2^64))=74`.
This folds four whole platform namespaces into unused valid field states
**without adding a bit**. It does not, by itself, shorten Apple's existing
74-bit contents, and specialized short-ID profiles remain better for small
numeric identifiers. Tags must be stable and versioned.

The general optimization for `m` subordinate namespaces is: pack all
admissible variants inside the unused states of an existing bounded field
before allocating new tag bits.

#### Theorem 3: range-tier modes with explicit fallback

For each admissible interval `[a_i,b_i)` of integer IDs, W metadata may
select the **range class** (not any identity bit), while payload stores
`x-a_i` in `ceil(log2(b_i-a_i))` bits. The decoder computes `x=a_i+r`;
it checks `r<b_i-a_i`. This is reversible and optimal *within the class*.

Example: a platform's 64-bit numeric ID uses **32 bits** when `x<2^32`
and **64 bits otherwise**. The latter route is mandatory; this is not
universal 32-bit compression. The two-bit 4-service tag can be added inside
the payload if the W profile identifies a numeric-family layout.

More sophisticated schemes can use intervals based on an analytically
specified model (not a lookup table of songs). A mode selector can choose
the shortest admissible representation **after accounting for all headers,
CRC, RS, column rounding and W overhead**.

#### Theorem 3a: harvest byte-alignment slack for **free moments**

A byte-aligned Reed-Solomon block wastes some of its final data byte.
For `b` source bits, fixed CRC-16 and four parity bytes, the number of
unused pre-RS bits is exactly:

`slack(b) = 8*ceil((b+16)/8) - (b+16)`, in `[0,7]`.

A separately designated W time-width profile may put a `t`-bit moment
inside these unused positions with **zero change in payload column count**
whenever `t<=slack(b)`. The moment is still part of the CRC-covered source
message. The decoder learns its exact width from mode metadata; values
outside the window use a longer fallback.

Examples under the research profiles:
- Full 131-bit Spotify rank: `slack(131)=5`, so times 0..31 seconds
  can be represented **inside the same 23 payload columns** as no moment.
- Canonical independent Spotify+YouTube pair: `slack(195)=5`, giving
  an exact 0..31-second moment **inside the same 31 columns**.
- Four-service 32-bit numeric mode: `b=2+32=34`, `slack(34)=6`,
  so up to 63 seconds can be represented in the same **11 columns**.
- Canonical YouTube Music, `b=64`, `slack(64)=0`: there is no
  extra room without an additional column.

This is a measurable **bit-allocation optimization**, not a compression of
uniformly random data. A W mode explicitly marking tiny time is necessary:
without it, a decoder would mistake those bits for zero padding.
W continues to hold *only* routing metadata.

#### A practical impossibility bound: 13-column universal YouTube

Suppose a **single** W layout must encode any of the `2^64` canonical
YouTube identities in 13 byte-carrying payload columns, without weakening
CRC-16 or four RS parity bytes. Only `13-4-2=7` data bytes remain: at most
`2^56` distinct IDs fit, which is just **1/256** of the required domain.
Therefore **13 payload columns cannot cover all 64-bit YouTube IDs** with
the same protection and the current eight-bit optical alphabet.

Even generously allocating **all 16** distinguishable W metawords to
different 13-column routing classes yields at most
`16 * 2^56 = 2^60 < 2^64` identities, and that would leave no metadata
states for any other layout or timestamp. With no ID data permitted in W,
a 14-column specialized canonical-YouTube frame is the firm lower bound
**within the present CRC+RS byte-frame construction**. This is not a claim
that every conceivable nonlinear channel code needs 14 symbols: the
claim expressly assumes unchanged CRC-16 and four systematic RS bytes.

#### Another bound: variable optical length is not free storage

If a decoder reliably distinguishes length classes `b_1,..,b_k` and their
routing modes, their *combined* capacity is at most
`sum_i 2^(b_i)`. Length is useful **side information**, but it cannot
magically carry dozens of bits in a code with only a few detectable lengths.
In particular, shorter variants cannot represent all inputs from a uniform
large space; there must always be fallback. Nor can the W's sixteen
metawords provide an extra eight payload bits: the absolute maximum is
four bits **before** subtracting the mandatory layout metadata.

**Profile count update:** the original adaptive-research analysis assumed a four-bit routing header with only 16 possible values. The current W transmits a **six-bit profile** with 64 values, of which 16 currently have codec implementations. Old scarce-header allocation arguments must use this updated capacity; packing identities into W is still forbidden.

## WASM and CLI integration

Browser-side V2 exports are `v2_encode_url`, `v2_encode_dual`, `v2_render_svg`, `v2_render_png`, `v2_decode_frame`, and `v2_scan_image`. Their experimental JSON format includes `version: 2` and `anchor: "round-dot-w-bch60"`. Scanning additionally returns W-local orientation/geometry and `anchor_corrected_bits`. The stable V1 WASM ABI remains unchanged.

```powershell
git fetch origin
```

- [x] One Rust V2 branch and one canonical spec file.
- [x] Fixed W contour and preserved negative-space channel, 60 smaller variable interior dot sites, exact 12-bit version and 6-bit profile.
- [x] Verified BCH(60,24,d≥13) subcode and bounded six-bit correction at correctly located sites.
- [x] Adaptive source profiles, legacy payload fallback, CRC16/RS4, browser V2 ABI, CLI, and demonstration PNG+SVG scans.
- [x] Existing CI run passed on Linux, Windows and macOS as checked on the current experimental branch.
- [ ] Repeated **real mobile camera** tests, varied physical print widths and materials, small-code blur, glare, clutter, severe tilt and occlusion; establish thresholds, latency and false-positive rates.
- [ ] Compare equal minimum reliably-scannable physical dimensions against stable V1; a smaller symbolic column count does not establish a smaller readable code.

- [ ] Consolidate test fixtures and other temporary experiment files only when their proven behavior is retained by tests. Run complete CI before merging to main.
