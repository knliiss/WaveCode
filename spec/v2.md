# WaveCode V2 — Optical Format Specification

**Version:** 2 · **Scope:** normative binary/optical format, decoding, interoperability and geometry. V1 remains separately specified in [V1](v1.md) and its existing frames are unchanged. Only the 22-capsule W-anchor variant described here identifies V2; earlier design prototypes do not.

## Format invariants

- The original WaveCode W is the optical finder at the logical left, used to determine its own position, direction, scale and mild perspective. **Its physical size is independent from the payload's scale**.
- The W transmits **only the explicit 12-bit optical version**. There is NO platform routing profile, time information, track ID, checksum of identity or style information in the logo.
- The W has **22 solid rounded capsules and zero microholes**, suitable for physical prototyping without tiny perforations.
- Dual profiles 17/18/19/14/16 infer their mode from **27–31 payload columns**. Special small-ID profiles 34/22–33 use an **RS-protected source marker** to share lengths **14–26** with Single formats; profiles 20/21 use the same principle for 32/33-column Dual. Conventional modes retain one optical profile column. Neither the W nor visual spacing encodes a track or source profile.
- `Classic` and `Compact` are only visual presets; they never alter `Frame.metadata`, `Frame.symbols`, identity or moment. The image scanner does not require knowing the preset.
- CRC-16/CCITT-FALSE covers the routing profile and identity payload, with four Reed–Solomon parity bytes protecting the identity payload and CRC.

## Geometry and exact 12-bit version in the W

The exact original brand geometry lives in `assets/brand/wavecode-mark.svg`. In the original 512×512 SVG coordinate system, eleven upper and eleven lower capsules have 20-unit width and a 34-unit horizontal step; centers are `x=86+34*i` for `i=0..10`. Upper ends face the fixed middle boundary `y=242`; lower starts face `y=274`. The **32-unit empty central channel and horizontal centers never vary**, and there are never small internal holes. Original upper heights are `[96,77,48,37,70,113,70,34,53,76,98]`, and lower heights `[30,50,70,87,59,31,56,85,66,47,29]`.

Each of the 22 capsules carries ONE protected version bit using a very small outward extension of its original length:

- Upper capsule bit `0` = original length; bit `1` = 5 original SVG units longer **toward its outer top** (upper edge moves up, central edge stays unchanged).
- Lower capsule bit `0` = original length; bit `1` = 5 original SVG units longer **toward its outer bottom** (lower edge moves down, central edge stays unchanged).
- Bit positions `0..10` are the upper capsules from left to right, positions `11..21` the lower capsules from left to right.
- The rendering canvas includes 5-unit extra vertical room on both sides (scaled); the 32-unit central gap is preserved.
- Five SVG units are about 0.42 mm at a printed W width of 30 mm. This is a geometric difference, **not a guarantee** that a particular printer or camera resolves it.

### Version BCH(22,12,d≥5)

Take binary primitive narrow-sense BCH(31,21,d≥5) with GF(32) polynomial `x^5+x^2+1`; the binary generator is `0x769` (degree 10). Shorten nine leading information coordinates to derive **BCH(22,12,d≥5)**. For `version ∈ [0,4095]`:

```text
m = version
word22 = (m << 10) OR remainder_GF2((m << 10), generator=0x769)
```

Place the 22 bits **most-significant first** into the upper then lower capsules. No routing profile or aesthetic selector enters this operation.

The code is linear. Exhaustive enumeration of all 4095 nonzero version codewords finds minimum Hamming weight **5**; therefore minimum distance is 5. Any one or two incorrectly classified capsule-length bits can be corrected uniquely; three or more are NOT guaranteed correctable or even detectable. The camera must still identify the actual 22 bars before this algebraic guarantee applies.

The reader first recognizes the characteristic W spacing, pairs capsule components, resolves camera roll, and estimates each capsule's **local scale from neighboring column centers**. It measures relative lengths, BCH-decodes the 12-bit version, requires exact `version=2`, and only then reads payload columns. W orientation tells the scanner the positive logical direction toward data. This method is significantly less demanding to manufacture than 60 tiny negative-space holes, and depends on sufficient image resolution, signal separation and camera perspective for reliable length classification.

## Payload profile, byte mapping and styles

`Frame` still has `metadata: u8` and RS-protected `symbols: Vec<u8>`. Standard source profiles print one extra leading optical metadata byte, which is CRC-covered but not individually RS-protected. Self-delimiting Dual lengths **27–31** omit it entirely and infer metadata by the visible column count; tiny Dual **14–26** and full Dual **32/33** codewords omit the header and instead begin with a protected source marker inside the RS codeword. The first byte of those codewords is ≥128, whereas a separately printed metadata symbol is <64. The scanner tests both 32/33 interpretations under RS and CRC when needed, including errors in the marker, and refuses ambiguous results. W carries optical version only.

### Independent 256-symbol optical alphabet and freely chosen gaps

Each byte appears as two opposed capsules of **constant width** and 16 height levels: `upper = byte >> 4`, `lower = byte & 15`. Physical rail height is `H × (0.085 + 0.022 × level)`, width is `0.75 × pitch`. No information is encoded in width, central gap or W-to-payload gap. `Classic` has `pitch=18, H=210, quiet=18`; `Compact` has `pitch=16, H=210, quiet=16`.

**Both whitespace distances are visual-only and independent.** `VisualSpacing` accepts:
- `payload_center_gap` — actual white distance between payload's upper and lower capsule boundaries, in output pixels;
- `logo_payload_gap` — actual white distance from the rightmost edge of W to the first payload capsule, in output pixels.

Both default to values chosen for V2 aesthetics: `payload_center_gap = 16 × H/232` (about **14.48 px** at H=210, half the W's 29 px white channel), and `logo_payload_gap = 1.4 × pitch` (**25.2 px Classic**, **22.4 px Compact**), larger than the preceding version. The original W has **its own unchanged 32-unit SVG central slit**.

Renderer interfaces: `RenderProfile::metrics_with_spacing`, `render_svg_with_spacing`, `render_png_with_spacing` in Rust; `v2_render_svg_with_spacing` / `v2_render_png_with_spacing` in WASM. For independent W size use `RenderProfile::metrics_with_spacing_and_logo_height_for_frame`, `render_svg_with_spacing_and_logo_height`, `render_png_with_spacing_and_logo_height` in Rust or `v2_render_svg_with_geometry`, `v2_render_png_with_geometry` in WASM. The extra `logo_height` argument controls W size without changing payload height. Existing renderers default to `H_w=H_p`, preserving their prior appearance and signatures.

### Canonical center, independent white slits and W/payload scales

**The vertical reference is the midpoint of the W's slit, never the midpoint of its black silhouette.** The original SVG's slit bounds are `y=242` and `y=274`, so `C_svg=258`. Let `H_w` be the W's rendered 232-unit reference height and `H_p` the payload's independently chosen optical rail reference height. In the W-local coordinate system use `s=H_w/232` and `y=129` as origin:

```text
C_local = (258-129)*s = 129*s
W upper inner baseline = (242-129)*s = 113*s
W lower inner baseline = (274-129)*s = 145*s
W slit size = 32*s [unchanged]

P = VisualSpacing.payload_center_gap [visual-only]
G = VisualSpacing.logo_payload_gap [visual-only]
payload upper inner baseline = C_local - P/2
payload lower inner baseline = C_local + P/2
payload max rail height = 0.415*H_p
payload first capsule left edge = quiet + 360*s + G
payload_x (first column cell) = quiet + 360*s + G - (1-0.75)*pitch/2

W upper outer bound = -5*s
W lower outer bound = (232+5)*s
full top bound = min(-5*s, payload_upper_baseline-0.415*H_p)
full bottom bound = max(237*s, payload_lower_baseline+0.415*H_p)
margin = max(8px,0.038*max(H_w,H_p))
canvas height = full_bottom-full_top+2*margin
Y offset = margin-full_top
```

Apply the same Y offset to W and payload; the payload's two allowed extrema remain mirror-symmetric around the **W slit center**, although their empty central gaps are not required to match. The W's scale is `H_w/232`, while payload heights are encoded using `H_p` and optical column widths using the chosen `pitch`; **there is no required ratio between W dimensions and payload dimensions**. No bar is clipped when either visual height changes: the canvas grows with the bounds. A screenshot, print or scanner receives *only the visible marks*: neither gap nor either scale is written into `Content`, `Frame`, metadata, or the W version.

### Scanner must not assume either gap

The reader locates the 22 solid W capsules using their characteristic shape, spacing and version-length code. It **excludes those specific identified W components** and then locates the separate payload components to their logical right, without checking an expected W-to-payload distance. Upper and lower payload rails are paired by their observed horizontal positions. It independently estimates the **payload height unit** by fitting the sixteen allowed height levels to the measured rails and uses CRC/Reed–Solomon checks to validate candidate interpretations; **it must not derive payload height from the W scale**. The reader does **not** compare the observed central payload gap to the W gap or to a constant. Neither a preset name, a scale ratio, nor a gap measurement is an input to the decoder.

The synthetic optical test suite varies both gaps independently across several values, including tight but separated and very spacious layouts, and checks the unchanged decoded URL under rotations and inverted contrast. These checks establish the **format's independence from decorative distances**, not a claim that every imaginable physical mark remains readable: zero or blurred-out whitespace merges connected bars, very large bitmaps hit image-size resource limits, and strong blur, reflections, foreshortening or print defects can make components indistinguishable. The renderer requires both gaps to be finite and at least 2 px on its output scale.

For all conventional source profiles, `B` identity+moment bits require:

```text
N_RS_codeword = ceil((B + 16_CRC) / 8) + 4_RS
N_visible = N_RS_codeword + (0 if profile in {14,16} else 1)
```

The exact profile-14 and profile-16 source inputs are separately specified below. `Frame.symbols.len()` is always the number of **RS codeword symbols**, not the optical column count. The public `optical_column_count(frame)` and `RenderProfile::metrics_for_frame(frame)` compute the actual visible length. The 64-bit single YouTube Music case still uses 14 RS data symbols **plus one optical profile glyph = 15 visible columns**.

The W has exactly the same version geometry in `Classic` and `Compact`; no payload spacing value is encoded or implied by the optical version. Styled bytes remain unchanged. Sixteen height levels require good resolution; aesthetic preference alone is not proof of camera reliability.

## Single-link source payload

A conventional Single frame has a source layout and a time-present flag in the leading routing metadata. The normal metadata byte uses `layout = metadata >> 2` and `has_time = (metadata & 2) != 0`; bit 0 is zero. `Layout::Compact` is 0, `Layout::Full` is 1, and `Layout::Dual` is 2. The 4-bit tags below apply to **Compact Single**, not to the W locator.

| Tag | Original-platform identity | Source bits after tag |
| ---: | --- | --- |
| 0 | YouTube Music, 11 Base64URL symbols | 66 |
| 1 | YouTube video, 11 Base64URL symbols | 66 |
| 2 | YouTube Shorts, 11 Base64URL symbols | 66 |
| 3 | TikTok numeric video ID | 64 |
| 4 | Apple Music, 10-bit regional storefront index + 64-bit song ID | 74 |
| 5 | Deezer numeric track ID | 64 |
| 6 | TIDAL numeric track ID | 64 |
| 7 | Qobuz numeric track ID | 64 |
| 8 | Amazon Music, 10 base36 characters | 52 |
| 9 | Instagram Reel, 4-bit (`length−1`) + 1–16 Base64URL symbols | `6 × length` |
| 10 | `vt.tiktok.com` share link, 4-bit (`length−1`) + 1–16 Base62 symbols | `6 × length` |

The source tag consumes **4 bits**. The symbols of `Track::TikTokShort` use the same Base62 alphabet as Spotify and preserve character case. Compact encoding excludes Spotify, which uses the **Full Single** identity rank of 131 bits. Full encodes any supported track through the deterministic platform-ranked identity defined in [V1](v1.md).

A time-present frame appends one unsigned 16-bit seconds value (0–65535) after the identity. Absence and `Some(0)` are distinct. TikTok and Instagram do not support native moments; malformed pairings are rejected rather than silently dropping the time field.

For conventional frames, serialize bits most-significant first, zero-pad the final data byte, compute CRC-16 over the metadata byte followed by serialized payload, append the two-byte CRC, then four RS parity bytes. The metadata column is not part of the RS codeword; the decoder validates it through CRC. Adaptive source profiles may instead use the self-delimiting and RS-protected marker schemes specified below.

## Dual source profiles — complete reversible implementation

Two independent IDs and an optional timestamp remain exactly recoverable without a Spotify–YouTube correspondence database. Each RS codeword includes CRC-16 and **four GF(256) parity bytes**, correcting up to two unknown damaged byte symbols within that codeword.

| Profile | Exact source domain | Data bits | Physical columns |
| ---: | --- | ---: | ---: |
| **34** | Spotify rank exactly zero + canonical YouTube rank below 2^63; no time | 64 incl. marker | **14** |
| **22–33** | Canonical YouTube64 + small Spotify rank, no time or 8-bit time; **protected marker+flag** | 8N−48 at N=15..26 | **15–26** |
| 17 | Spotify rank below 2^104 + canonical YouTube64; no time | 168 | **27** |
| 18 | Spotify rank below 2^112 + canonical YouTube64; no time | 176 | **28** |
| 19 | Spotify rank below 2^120 + canonical YouTube64; no time | 184 | **29** |
| 14 | Spotify rank below 2^128 + canonical YouTube64; no time | 192 | **30** |
| 16 | **All Spotify22 + all YouTube Base64URL11 without time**, or mixed-radix low Spotify/canonical YouTube with 8-bit time | 200 | **31** |
| **20** | All Spotify22 × all YouTube Base64URL11; time absent or 0–255 | 207 | **32** |
| **21** | All Spotify22 × all YouTube Base64URL11; time 256–65535 | 214 | **33** |

Metadata for modes 17/18/19/14/16 is inferred solely from the **exact number of observed columns**, with no added marker or header column. Mode 34 for 14 columns has a protected `1` marker; modes 22–33 for 15–26 columns have a protected `10` (no time) or `11` (8-bit time) prefix. Modes 20/21 for 32–33 columns have a protected leading `1` marker. Existing single-link codes retain their **explicit metadata byte below 64**, giving disjoint clean first-byte ranges. All branches are CRC-validated after RS correction, and conflicting successful interpretations are rejected. Other existing single-link source modes (1,3,5,7,9,11,12) and compatible V2 fallback modes (0,2,4,6,8,10,13,15) are preserved. `encode_adaptive` chooses the fewest **visible columns**, favoring an all-RS-protected Dual marker over a separate unprotected header on ties. The W remains version-only.

## Mathematical Dual minimization and proven bounds

**Assumptions:** original opaque Spotify and YouTube IDs must both be recovered exactly offline, no lookup table or inferred inter-service relationship; 8 optical bits per column; a 16-bit CRC and 32-bit RS parity are preserved. These are conditional information-theory bounds for this format, not a statement that every possible alternative optical/ECC design is impossible.

Let `S=62^22` (`log2(S)≈130.9923188285`) and `Y=2^66` for arbitrary 11-symbol Base64URL YouTube IDs. Canonical YouTube video IDs have two fixed final bits, giving `Y_c=2^64`. A fixed-size lossless code over a domain of size `M` requires `ceil(log2 M)` information bits. With CRC16 and RS4, `N` columns can protect at most `8N-48` data bits. Therefore

```text
N >= ceil((ceil(log2 M) + 48)/8)
```

| Whole independent domain | Minimum bits | Proven lower bound |
| --- | ---: | ---: |
| Every Spotify22 + canonical YouTube64, no time | 195 | **31** |
| Every Spotify22 + arbitrary YouTube66, no time | 197 | **31** |
| Every Spotify22 + arbitrary YouTube66, 8-bit time | 205 | **32** |
| Every Spotify22 + arbitrary YouTube66, 16-bit time | 213 | **33** |
| Spotify rank below 2^128 + canonical YouTube64, no time | 192 | **30** |
| Spotify rank below 2^120 + canonical YouTube64, no time | 184 | **29** |
| Spotify rank below 2^112 + canonical YouTube64, no time | 176 | **28** |
| Spotify rank below 2^104 + canonical YouTube64, no time | 168 | **27** |

Modes 14 and 16 now **meet the no-time lower bound for both the restricted 128-bit/canonical case and the entire independent 22-character Spotify + arbitrary 11-character YouTube domain**. Profiles 20 and 21 meet the whole-domain 8-bit-time and 16-bit-time lower bounds. Specific pairs may still be representable with fewer columns by trading length against other pairs.

### Specialized 14–26-column codes and precise bounds

A **shorter code for a particular input** does not contradict the whole-domain bounds above. V2 now supports the following lossless, deterministic special cases without any built-in ID dictionary:

- **14 columns / profile 34:** if the Spotify numeric rank is exactly `0`, the YouTube ID is canonical, and its 64-bit rank fits `63` bits, encode one RS-protected leading `1` marker followed by those exact 63 YouTube bits. Source capacity is `14×8−48=64` bits. This precisely fits the complete `2^63`-value restricted subdomain, which could not all fit in 13 columns at the same CRC/RS strength.
- **15–26 columns / profiles 22–33:** for `N=15..26`, the first two source bits are `10` (no time) or `11` (8-bit time; `N≥16`). The remaining identity widths are `8N−114` bits for Spotify without time, or `8N−122` for Spotify with time. Each word then carries the full **64-bit canonical YouTube ID**. Every bit is used: `2 + Spotify_width + 64 + optional_8_time = 8N−48` information bits, plus 16 CRC bits and four 8-bit RS parity symbols = exactly `8N` physical bits. `Spotify_width` ranges from 6 to 94 without time and from 6 to 86 with time.
- Identifiers outside these bounds never truncate: they automatically use the next sufficiently large lossless class (27–31 columns without time, 31–32 columns with short time, or the full-domain 32/33 fallback). `None` and `Some(0)` remain distinct.
- These tiny profiles share optical lengths with some Single codes. The extra high marker lies **inside the RS codeword**, so it can be repaired; ordinary explicit metadata bytes are below 64. Both interpretations are attempted when appropriate and validated by their independent RS/CRC checks. Distance from the W, width, style and white slit **do not encode the mode**.

These are lower bounds only for the specified input subdomains under fixed CRC-16/RS4, not a universal assertion that 14 is the minimum for every single URL. Any shorter special case necessarily reduces the domain it covers, changes an error-protection constraint, or reserves yet another distinct framing class. There is no single fixed-size code that can represent the entire Spotify22 × YouTube66 domain with fewer than 31 columns under our assumptions.

### Exact 31-column mixed-radix encoding

Define `R=2^128`, `H=S×2^66`, `C=2^200`. For **every** no-time pair with `0≤spotify<S` and `0≤youtube<2^66`, encode `ordinal=spotify×2^66+youtube`, occupying `[0,H)`. For `spotify<R`, canonical 64-bit `youtube`, and `seconds≤255`, encode `t=spotify×2^72+youtube×256+seconds` as `ordinal=H+t`, only if `t<C-H`; otherwise fall back to 32-column mode 20. Each range is disjoint and has a precise arithmetic inverse. `H/C≈0.124336245747`, leaving about **87.5664%** of the low-Spotify/8-bit-time domain available in the same 31-column class. This is a *counting fraction*, not a claim about Spotify usage.

The entire 128-bit-Spotify/canonical-YouTube/8-bit-time class contains `C` tuples; adding the `H` no-time tuples would exceed 31-column capacity. The fallback for some short-time pairs is therefore mathematically necessary if **all no-time pairs** receive 31 columns while the present CRC/RS strength is retained.

### Source bits of 32- and 33-column frames

Mode 20 packs `1 marker + 1 time-present flag + 131 Spotify bits + 66 YouTube bits + 8 seconds = 207` bits, plus a zero pad bit to 26 bytes, plus two CRC bytes and four RS bytes: **32 columns**. The flag distinguishes absent time from `Some(0)`.

Mode 21 packs `1 marker + 131 Spotify bits + 66 YouTube bits + 16 seconds = 214` bits, plus two zero pad bits to 27 bytes, two CRC bytes and four RS bytes: **33 columns**. Only 256–65535 seconds use this mode. The marker is RS-protected in both cases; the decoder tries both implicit and explicit framing when the column count is 32 or 33.

## WASM, CLI and verification

WASM V2 entry points: `v2_encode_url`, `v2_encode_dual`, `v2_render_svg`, `v2_render_png`, `v2_render_svg_style`, `v2_render_png_style`, `v2_render_svg_with_spacing`, `v2_render_png_with_spacing`, `v2_render_svg_with_geometry`, `v2_render_png_with_geometry`, `v2_decode_frame`, `v2_scan_image`. JSON frames retain `metadata` for application interoperability; it is encoded as the first payload column for conventional profiles but **inferred from visual length for profiles 17–19/14/16, or from protected source markers for profiles 20–34**. Neither form modifies W. The scanner returns exact version, decoded payload profile, BCH correction count and W pose.

For Windows PowerShell (commands on ONE line, or use the PowerShell backtick to continue):

```powershell
cargo test --workspace
cargo run -p wavecode --example v2 -- encode-adaptive "https://music.youtube.com/watch?v=JGwWNGJdvx8&t=59" classic.png classic
cargo run -p wavecode --example v2 -- encode-adaptive "https://music.youtube.com/watch?v=JGwWNGJdvx8&t=59" compact.png compact
cargo run -p wavecode --example v2 -- scan classic.png
cargo run -p wavecode --example v2 -- scan compact.png
# Optional trailing W height (pixels) after the two visual gap parameters:
cargo run -p wavecode --example v2 -- encode-adaptive "https://music.youtube.com/watch?v=JGwWNGJdvx8&t=59" w-small.png classic 16 40 110
cargo run -p wavecode --example v2 -- scan w-small.png
```

Each output is a real PNG plus SVG. The W is represented as **22 solid capsule rectangles and zero microholes**. The V2 optical GitHub Actions workflow checks both render styles by decoding generated PNGs and publishes reproducible test vectors.
